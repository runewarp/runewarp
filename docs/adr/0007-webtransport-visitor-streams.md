# WebTransport Visitor streams and permit-backed credit

Accepted under [#254](https://github.com/runewarp/runewarp/issues/254) and [#256](https://github.com/runewarp/runewarp/issues/256), including its [credit-policy amendment](https://github.com/runewarp/runewarp/issues/256#issuecomment-6392362183). This supersedes ADR 0006's receive-slot carrier, maintenance and capacity decisions. HTTP/3 signaling, the event gate, required pinned-identity mTLS, no application 0-RTT and whole-connection session lifetime remain unchanged.

The Server opens one draft07 WebTransport bidirectional stream per Visitor on the established session. The Client accepts only streams delivered for its full session ID. The Server sends the internal PROXY v2 envelope and buffered ClientHello immediately, without a per-Visitor Client acceptance exchange. Raw Visitor bytes replace receive-slot DATA; there are no idle CONNECT requests. FIN half-closes each direction, and abort resets only that Visitor. Both peers must upgrade together.

Each Client connection reserves up to T = 256 idle credits from the same 1,024-permit Client-instance budget as active Visitors. An arrival transfers a reserved permit into its stream, and maintenance acquires replacements without blocking intake on handler work. Active concurrency can consume the whole budget on one connection; quiet connections can reserve 256 permits each. The Client's fork incoming, pending-prefix and per-session queue limits are all 256. Server pending-open and active-stream admission, least-active placement and no member retry remain unchanged.

## Explicit Quinn credit updates

The configured stream target equals held active plus idle permits after each update. All updates serialize under the controller's state mutex, set the held target, temporarily lower it to zero, then restore held before returning. No call sets a target above held permits. Quinn 0.11.11 and quinn-proto 0.11.19 batch MAX_STREAMS when the unsent increment is at most configured concurrency / 8. A plain update from eight to nine can therefore withhold a reserved ninth stream indefinitely. `set_max_concurrent_bi_streams(0)` reduces the threshold to zero and queues already-allocated credit; restoring held preserves that queued flag. This uses the behavior of `Connection::set_max_concurrent_streams`, `StreamsState::set_max_concurrent`, `queue_max_stream_id` and `ensure_remote_streams` in those exact versions. It follows the related lower-target technique in [Quinn maintainer guidance](https://github.com/quinn-rs/quinn/issues/1517#issuecomment-1474555820). Dependency upgrades must preserve or replace this behavior and pass the raw eight-to-nine and full-budget regressions.

Quinn takes a separate internal lock for each call. The three calls are not atomic to its driver or stream completions. The first held call allocates any newly permit-backed capacity. If the driver sends it before the zero call, it is already advertised; otherwise zero queues it. Restore does not clear that queued update. `max_remote` is monotonic, so neither lowering nor concurrent completion retracts those stream IDs. A completion during zero cannot allocate a replacement at zero; restore may allocate one afterward. A completion outside zero may allocate one immediately. Those additional replacements can exceed useful idle credit when a finished stream's handler retains its permit, just as with a single held-target update; the temporary lower target creates no larger configured capacity. They are irrevocable transport credit, not new handler reservations.

The Client therefore keeps the no-wait over-issue guard. An arrival without idle credit tries the aggregate budget exactly once. On failure it resets and stops the stream before handing it to a handler, with existing saturation log throttling. Received reset codes are never part of the contract. Tests distinguish transport-finished/handler-retained over-issue from normal burst and full-budget simultaneous admission, which have zero guard resets. Concurrent completion has zero guard resets with handler headroom or when handlers release before replacement opens. At an exhausted budget, a replacement can arrive before the previous handler releases its final half, including under ordinary production scheduling. The guard rejects it; zero resets across that window are not promised. The deterministic one-permit retained-handler test reaches the same guard with a plain held-target setter, independently of the temporary-zero update.

## Drop ownership and teardown

Both application halves retain one shared lease. A two-half atomic counter invokes the resource callback exactly once, from the final half's Drop, before that half's transport fields drop. The callback lowers held and completes the serialized target update. Each half declares its transport fields before its lease field, so the semaphore permit in the lease survives both transport-field drops, including concurrent Drops. Completed or failed writes retain their transport handle until application Drop. This suppresses replacement allocation caused by final handle release; it cannot suppress FIN/ACK/EOF freeing Quinn state earlier, which is why the guard remains mandatory.

Connection termination releases idle permits even when the Client handle remains retained. Active permits remain with their application halves until Drop. GOAWAY seals new opens while committed pending opens and active Visitors count toward drain. A session close or CONNECT end closes the entire Tunnel with `H3_NO_ERROR`, resets active Visitors and uses normal address-worker reconnect; no session is reopened on that connection.

## Graceful completion boundary

Server-local proxy completion only enqueues its final bytes and FIN. The pinned h3-quinn `poll_finish` does not wait for acknowledgment or application consumption, and the fork's terminal session guard rejects even buffered unread bytes once the connection ends. Closing the connection at local Drop can therefore lose a valid final tail.

After local Visitor work and earlier signaling requests finish, the Server sends the standard `DRAIN_WEBTRANSPORT_SESSION` capsule through the pinned session API and keeps driving HTTP/3. The Client keeps accepting queued Visitors and waits for its Visitor leases to release, then sends CLOSE as its completion acknowledgment. The Server observes CLOSE and closes the whole Tunnel. Successful production proxies have already received the Client's FIN before local completion, so their Client streams have been handed off and own leases before DRAIN. Queued application streams also own leases. Aborted proxies do not gain a delivery guarantee. No per-Visitor acceptance exchange or private byte framing is added.

DRAIN leaves the session live. CLOSE, CONNECT end, revocation, cancellation and transport errors retain immediate termination behavior. Both graceful phases share the existing whole-connection deadline; a Client retaining a stream can delay completion only until that deadline. This changes the former local-only drain boundary, while preserving FIN half-close and the session-end contract. It needs no fork, dependency or receive-window change.

The fork and all four h3 pins remain `df27106fb243baaf867d11441d11cf671ec9da7e`. The 16 KiB decoded-header limit, 64 MiB shared connection receive window and 1,250,000-byte stream window remain unchanged. Shared-window starvation, periodic Server classifier eviction, bodyless 429 admission and deferred parser hardening retain their documented limits. Higher budgets, window tuning, withdrawal and Public QUIC remain separate work.
