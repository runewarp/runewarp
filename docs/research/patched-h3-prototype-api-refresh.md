# PROTOTYPE: `h3` + `h3-quinn` API refresh

## Scope

This note supports the patched-Hyperium stack prototype for [#239](https://github.com/runewarp/runewarp/issues/239). It refreshes released-source facts needed to interpret the prototype. It is not a production-stack selection, protocol specification, or compatibility commitment.

Evidence was refreshed on 2026-08-13 from upstream release tags, current upstream source, crates.io metadata, and the governing RFCs.

## Released interface and gap matrix

| Required seam | Released public interface | Concrete gap or constraint |
| --- | --- | --- |
| Arbitrary local SETTINGS | Client and Server builders configure only known settings such as maximum field size, Extended CONNECT, and H3 Datagram ([client builder](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/client/builder.rs#L62-L112), [server builder](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/server/builder.rs#L51-L119)). The unstable extension feature exposes constructible `SettingId` and `Settings::insert`. | No builder or connection-construction path accepts those raw entries; config conversion always builds its own fixed known set. The frame store is also fixed at eight entries ([frame source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/proto/frame.rs#L388-L489)). |
| Raw unknown peer SETTINGS | The control driver decodes the peer SETTINGS frame and publishes typed known values through shared connection state. | The decoder inserts only identifiers in its fixed `is_supported` set and discards every other non-forbidden pair after an optional debug log ([decoder](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/proto/frame.rs#L400-L410), [discard path](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/proto/frame.rs#L523-L560)). Runewarp therefore cannot observe its capability setting. RFC 9114 requires unknown settings to be ignored by generic H3 semantics, but an extension that defines one must be able to consume it ([RFC 9114 §7.2.4.1](https://www.rfc-editor.org/rfc/rfc9114.html#section-7.2.4.1)). |
| Exact GOAWAY | Internal `ConnectionInner::shutdown` can encode a caller-supplied typed identifier ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/connection.rs#L326-L353)). Public Server `shutdown(max_requests)` instead derives a boundary from `last_accepted_stream + max_requests` ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/server/connection.rs#L156-L167)). | There is no high-level method accepting the exact first-unprocessed request stream ID and updating native shutdown state. Calling the exposed inner method with separate state would not update Server's private `sent_closing`, which controls request rejection ([state](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/server/connection.rs#L43-L61)). RFC 9114 defines the GOAWAY identifier as exclusive: requests with IDs greater than or equal to it are unprocessed ([RFC 9114 §5.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-5.2)). |
| Narrow Extended CONNECT dispatch | A resolved known `:protocol` is inserted into `http::Request::extensions`, so ordinary request dispatch is otherwise usable ([request resolution](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/server/request.rs#L218-L258)). Builders expose `SETTINGS_ENABLE_CONNECT_PROTOCOL`. | Released `ext::Protocol` represents only `webtransport` and `connect-udp`; `FromStr` rejects all other values ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/ext.rs#L5-L45)). A Runewarp-specific protocol token is therefore decoded as a malformed request and needs a narrow arbitrary-token representation, not a generic extension registry. Extended CONNECT over H3 is governed by [RFC 9220 §3](https://www.rfc-editor.org/rfc/rfc9220.html#section-3). |
| Directional cancellation | Client and Server request streams expose caller-selected `h3::error::Code` through `stop_sending` and `stop_stream`; send, finish, and receive APIs remain ordinary H3 request-stream operations ([common request stream](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/connection.rs#L1028-L1102)). | No dependency patch is inherently required for caller-selected STOP_SENDING and RESET_STREAM codes. |
| H3 Datagram send, receive, and request routing | `h3-quinn`'s optional feature backs send and receive handler traits with Quinn connection clones ([adapter](https://github.com/hyperium/h3/blob/2dc3412bdf6083451920d5bfd7a9484d054c1859/h3-quinn/src/datagram.rs#L21-L73)). `h3-datagram` exposes per-request senders plus a reader returning the decoded request stream ID ([handlers](https://github.com/hyperium/h3/blob/230744a80ad49aa14ae68c4b9698fb6260992dbd/h3-datagram/src/datagram_handler.rs#L17-L110)). This matches RFC 9297's Quarter Stream ID routing model ([RFC 9297 §2.1](https://www.rfc-editor.org/rfc/rfc9297.html#section-2.1)). | Released `h3-datagram` 0.0.2 computes the encoded Quarter Stream ID but stores a zero-filled buffer, so every outgoing Datagram is serialized with Quarter Stream ID 0 ([released defect](https://github.com/hyperium/h3/blob/230744a80ad49aa14ae68c4b9698fb6260992dbd/h3-datagram/src/datagram.rs#L67-L77)). Upstream fixed this on 2026-08-07 in [`ebd4260`](https://github.com/hyperium/h3/commit/ebd426036d2a81ae9cee43337f43ae8ccc819404), after all three released tags. The sender does not itself enforce bilateral `SETTINGS_H3_DATAGRAM = 1`, despite [RFC 9297 §2.1.1](https://www.rfc-editor.org/rfc/rfc9297.html#section-2.1.1); the adapter must gate it using local configuration and patched peer SETTINGS. `Datagram::new` also asserts rather than returning an error for an invalid request stream ID ([source](https://github.com/hyperium/h3/blob/230744a80ad49aa14ae68c4b9698fb6260992dbd/h3-datagram/src/datagram.rs#L18-L30)). The API does not expose the live maximum Datagram size; the adapter can retain the original `quinn::Connection` clone for that measurement. |
| Capsule stream access | Request streams expose incremental H3 DATA send and receive. RFC 9297 defines the H3 Capsule data stream as the bytes carried by DATA frames and warns against buffering a complete Capsule value before processing ([RFC 9297 §§3.1–3.2](https://www.rfc-editor.org/rfc/rfc9297.html#section-3.1)). | Released `h3`, `h3-quinn`, and `h3-datagram` contain no Capsule codec. A bounded streaming Capsule codec can remain inside the Runewarp prototype adapter; library-level Capsule API is not required merely to exchange lifecycle Capsules. Packet data must not use a reliable Capsule fallback. |
| Connection teardown | The Client driver exposes `poll_close` and `wait_idle` and must be continuously driven ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/client/connection.rs#L389-L486)). Server Connection drop closes QUIC with `H3_NO_ERROR` ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/server/connection.rs#L301-L312)); dropping the last Client `SendRequest` does likewise ([source](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/client/connection.rs#L251-L267)). | There are no library-spawned runtime tasks, but there is also no symmetric Server wait-for-idle/closed handle. `h3-quinn::Connection` stores a private Quinn clone and provides no accessor ([source](https://github.com/hyperium/h3/blob/2dc3412bdf6083451920d5bfd7a9484d054c1859/h3-quinn/src/lib.rs#L40-L65)). The adapter can retain the original Quinn clone and own every task/stream explicitly. A narrow accessor is optional convenience, not demonstrated protocol necessity. Graceful and immediate shutdown remain governed by [RFC 9114 §§5.2–5.3](https://www.rfc-editor.org/rfc/rfc9114.html#section-5.2). |

## Smallest defensible dependency patch

The prototype evidence supports this bounded patch shape:

1. In `h3`, make arbitrary non-forbidden setting identifiers constructible, retain unknown peer pairs, expose lookup/iteration, and let builders add validated local pairs.
2. In `h3`, represent an arbitrary syntactically valid Extended CONNECT protocol token while preserving the existing `http::Request::extensions` dispatch path.
3. In `h3`, expose exact first-unprocessed Server GOAWAY through the high-level connection so frame emission and request-rejection state cannot diverge.
4. In `h3-datagram`, carry the upstream Quarter Stream ID serialization fix with its regression test.
5. Patch `h3-quinn` only if the prototype demonstrates that retaining the original Quinn clone cannot provide adequate Datagram-ceiling or teardown ownership. Do not add Runewarp semantics or a generic plugin framework.

Capsule framing belongs in the Runewarp adapter for this experiment. Existing request DATA, response, cancellation, and finish APIs are sufficient substrate.

## Current-upstream check

At sampled upstream `master` commit [`b986a537ddb1ccdd1eca3685b883cf7549ff7698`](https://github.com/hyperium/h3/commit/b986a537ddb1ccdd1eca3685b883cf7549ff7698), the Quarter Stream ID defect is fixed. Arbitrary SETTINGS, arbitrary Extended CONNECT tokens, exact high-level Server GOAWAY, and symmetric teardown access remain absent. Current upstream has added more fixed protocol constants, but that does not provide a private Runewarp token.

These are source/API facts, not proof that the proposed patches are correct. The dependency tests and production-shaped Runewarp acceptance matrix must supply that proof.

One pre-existing conformance limitation remains relevant: released `h3` declares `SettingsError::InvalidSettingValue` but does not validate that received `SETTINGS_H3_DATAGRAM` is only `0` or `1` ([decoder](https://github.com/hyperium/h3/blob/22c1aa3f44d1463cd7644c8f654fffc9a6da305c/h3/src/proto/frame.rs#L486-L570), [RFC 9297 §2.1.1](https://www.rfc-editor.org/rfc/rfc9297.html#section-2.1.1)). Fixing it is compatible with the SETTINGS patch, but it must be itemized separately rather than attributed to Runewarp policy.
