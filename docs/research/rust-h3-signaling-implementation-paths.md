# Rust HTTP/3 implementation paths for Tunnel signaling

Research asset for [Research maintained Rust HTTP/3 implementation paths for signaling](https://github.com/runewarp/runewarp/issues/238), current on 11 August 2026. It evaluates the exact planning contract resolved by [Map association signaling onto ordinary HTTP/3](https://github.com/runewarp/runewarp/issues/226). It neither implements signaling nor selects the future Visitor carrier.

## Verdict

**Cloudflare quiche 0.29.3 is the only maintained, published Rust stack surveyed whose public APIs can realize the complete signaling contract without patching its HTTP/3 layer.** It can send arbitrary additional SETTINGS and retain unknown peer SETTINGS, drive ordinary requests and responses, apply direction-specific QUIC stream shutdown with standard H3 codes, send caller-selected GOAWAY identifiers, expose the peer certificate, and leave early data disabled. Its cost is a transport replacement: Runewarp would exchange Quinn + rustls for quiche's lower-level packet/event-loop API and BoringSSL integration. Exact certificate-required mTLS also needs a custom public `SslContextBuilder`; quiche's convenience `verify_peer(true)` deliberately still permits a peer that presents no certificate. [quiche H3 configuration](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Config.html) [quiche H3 connection](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Connection.html) [quiche QUIC configuration](https://docs.rs/quiche/0.29.3/quiche/struct.Config.html) [quiche QUIC connection](https://docs.rs/quiche/0.29.3/quiche/struct.Connection.html)

**`h3` 0.0.8 + `h3-quinn` 0.0.10 is the lowest-churn integration path, but not an exact unmodified implementation path.** It aligns with Runewarp's existing Quinn 0.11 and rustls 0.23 dependencies and supplies ordinary request/response and cancellation primitives. Its public configuration exposes only settings known to the crate, and its peer `Settings` projection discards unknown settings. Its server shutdown API accepts a count relative to the last accepted stream instead of the exact first-unprocessed stream ID required by the settled GOAWAY contract. Supporting Runewarp therefore requires an upstream extension or a maintained fork at the H3 layer. Upstream still labels `h3` experimental. [Runewarp dependencies](../../Cargo.toml) [`h3` status](https://github.com/hyperium/h3/tree/h3-v0.0.8#status) [`h3` configuration source](https://github.com/hyperium/h3/blob/h3-v0.0.8/h3/src/config.rs) [`h3` server shutdown source](https://github.com/hyperium/h3/blob/h3-v0.0.8/h3/src/server/connection.rs)

**`s2n-quic` 1.86.0 does not provide a production H3 alternative.** AWS's in-tree `s2n-quic-h3` adapter declares itself unpublished and for testing only. It implements hyperium `h3`'s transport traits, so arbitrary SETTINGS and exact GOAWAY remain limitations of the same `h3` layer, while adoption would also replace Runewarp's QUIC transport. The separately published community crate of the same name also binds s2n-quic to hyperium `h3`; it does not supply a different HTTP/3 implementation. [s2n-quic repository](https://github.com/aws/s2n-quic) [AWS test-adapter manifest](https://github.com/aws/s2n-quic/blob/main/quic/s2n-quic-h3/Cargo.toml) [community adapter registry entry](https://crates.io/crates/s2n-quic-h3/0.2.0)

No surveyed stock stack can promise compatibility with every possible future Visitor carrier before that carrier is selected. quiche exposes the broadest combination of H3 and underlying QUIC controls; `h3` exposes ordinary requests, HTTP Datagrams, Extended CONNECT and experimental WebTransport features. A future carrier must still be checked against the selected stack's stream ownership and extension APIs. This research does not choose it.

| --- | --- | --- | --- |

| Inspect mandatory peer marker | **Yes:** `peer_settings_raw` includes unknown settings | **No:** unknown settings are decoded internally but omitted from public `Settings` | **No:** same `h3` layer |

## Why quiche meets the signaling seam

quiche's H3 configuration accepts arbitrary non-conflicting `(identifier, value)` pairs, and `peer_settings_raw()` returns the received raw list including unknown settings. The fixed Runewarp identifier is therefore representable without modifying quiche. quiche maps a wholly missing SETTINGS frame to `H3_MISSING_SETTINGS`; after a valid frame arrives, Runewarp can map an absent marker to `H3_GENERAL_PROTOCOL_ERROR`, a value other than `1` to `H3_SETTINGS_ERROR`, and normal termination to `H3_NO_ERROR` through the application-error close API. [quiche `set_additional_settings`](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Config.html#method.set_additional_settings) [quiche `peer_settings_raw`](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Connection.html#method.peer_settings_raw) [quiche H3 errors](https://docs.rs/quiche/0.29.3/quiche/h3/enum.WireErrorCode.html)

Its request API opens an ordinary client-initiated H3 request stream and can end HEADERS with FIN; the Server polls HEADERS/DATA/Finished events and sends response HEADERS/body/FIN. quiche intentionally leaves HTTP semantic validation to the application, which permits Runewarp's exact method, authority, content, and delayed bodyless `204` rules. [quiche H3 module](https://docs.rs/quiche/0.29.3/quiche/h3/) [`send_request`](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Connection.html#method.send_request) [`send_response`](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Connection.html#method.send_response)

At the QUIC layer, `stream_shutdown(Read, code)` discards receive input and emits STOP_SENDING; `stream_shutdown(Write, code)` drops the send side and emits RESET_STREAM. This directly represents the directional `H3_REQUEST_CANCELLED` and `H3_REQUEST_REJECTED` actions from the settled contract. Connection-wide failures can use `Connection::close(true, h3_code, reason)`. [quiche `stream_shutdown`](https://docs.rs/quiche/0.29.3/quiche/struct.Connection.html#method.stream_shutdown) [quiche `close`](https://docs.rs/quiche/0.29.3/quiche/struct.Connection.html#method.close) [RFC 9114 error codes](https://www.rfc-editor.org/rfc/rfc9114.html#name-http-3-error-codes)

`send_goaway(id)` exposes the wire identifier, but quiche's API documentation describes the Server value as the "highest processed request", while RFC 9114 defines requests at or above the identified Client-initiated bidirectional stream ID as rejected. Runewarp must pass its settled first-unprocessed boundary, stop opening requests after the peer event, and explicitly cancel inbound streams at or above the boundary. This semantic mismatch deserves a focused conformance fixture before adoption. [quiche `send_goaway`](https://docs.rs/quiche/0.29.3/quiche/h3/struct.Connection.html#method.send_goaway) [RFC 9114 §5.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-5.2)

For mTLS, the convenience `verify_peer(true)` requests and verifies a presented Client certificate but expressly permits anonymous Clients. The public `with_boring_ssl_ctx_builder` route allows BoringSSL's `PEER | FAIL_IF_NO_PEER_CERT` verification mode, trusted roots, Server certificate, and key to be configured before handing the context to quiche. Runewarp must then extract the verified leaf through `peer_cert()` for its Client identity. This is feasible but materially more complex than its current rustls verifier. [quiche certificate-verification behavior](https://docs.rs/quiche/0.29.3/quiche/struct.Config.html#method.verify_peer) [quiche custom BoringSSL context](https://docs.rs/quiche/0.29.3/quiche/struct.Config.html#method.with_boring_ssl_ctx_builder) [BoringSSL Rust verification modes](https://docs.rs/boring/latest/boring/ssl/struct.SslVerifyMode.html) [quiche `peer_cert`](https://docs.rs/quiche/0.29.3/quiche/struct.Connection.html#method.peer_cert)

Early data is off unless `Config::enable_early_data()` is called. Runewarp can retain ticket-based resumption while never enabling or acting during early data. This requires a test asserting that neither requests nor future assignment availability become visible before handshake completion and bilateral SETTINGS. [quiche `enable_early_data`](https://docs.rs/quiche/0.29.3/quiche/struct.Config.html#method.enable_early_data) [quiche session API](https://docs.rs/quiche/0.29.3/quiche/struct.Connection.html#method.session)

## Why the Quinn-aligned path needs H3 work

`h3-quinn` adapts Quinn to the generic `h3` transport traits and clones the underlying `quinn::Connection`, so it fits Runewarp's current runtime and can preserve access to the same QUIC connection. `h3` supplies ordinary typed request streams, split send/receive halves, STOP_SENDING controls, standard error `Code` values, and graceful shutdown. [`h3-quinn` source](https://github.com/hyperium/h3/blob/h3-v0.0.8/h3-quinn/src/lib.rs) [`h3` client request stream](https://docs.rs/h3/0.0.8/h3/client/struct.RequestStream.html) [`h3` server request stream](https://docs.rs/h3/0.0.8/h3/server/struct.RequestStream.html)

The blockers are above Quinn. `h3`'s public Client and Server builders configure only the settings understood by the crate. Although the internal frame parser retains arbitrary setting identifiers, conversion to the public peer `Settings` copies only the known fields; applications cannot add or read the Runewarp marker. The public Server `shutdown(max_requests)` derives GOAWAY from `last_accepted_stream + max_requests`, rather than taking the settled exact boundary. These are small conceptual extensions but protocol-critical owned code if carried as a fork. [`h3` settings projection](https://github.com/hyperium/h3/blob/h3-v0.0.8/h3/src/config.rs) [`h3` client builder](https://docs.rs/h3/0.0.8/h3/client/struct.Builder.html) [`h3` server builder](https://docs.rs/h3/0.0.8/h3/server/struct.Builder.html) [`h3` shutdown implementation](https://github.com/hyperium/h3/blob/h3-v0.0.8/h3/src/server/connection.rs)

Quinn itself is not the blocker: Runewarp already uses its rustls integration; Quinn's ServerConfig accepts a custom rustls configuration, `Connection::handshake_data` exposes negotiated TLS data, `Connection::close` accepts application codes, and 0-RTT requires an explicit `into_0rtt` path. [Quinn `ServerConfig::with_crypto`](https://docs.rs/quinn/0.11.11/quinn/struct.ServerConfig.html#method.with_crypto) [Quinn `handshake_data`](https://docs.rs/quinn/0.11.11/quinn/struct.Connection.html#method.handshake_data) [Quinn `close`](https://docs.rs/quinn/0.11.11/quinn/struct.Connection.html#method.close) [Quinn `into_0rtt`](https://docs.rs/quinn/0.11.11/quinn/struct.Connecting.html#method.into_0rtt)

## Integration risk and recommendation

1. **If the contract must be implemented from published, unmodified dependencies now, prototype quiche 0.29.3.** Gate adoption on fixtures for the exact custom SETTINGS outcomes, first-unprocessed GOAWAY boundary, both cancellation directions, required Client certificate failure, identity extraction, and absence of application 0-RTT. Benchmark it before accepting the event-loop and BoringSSL migration.
2. **If preserving Quinn + rustls is the stronger engineering constraint, first upstream or isolate the two missing `h3` seams.** Require arbitrary local/peer SETTINGS and an exact GOAWAY identifier API behind a narrow Runewarp-owned adapter. Do not implement the protocol directly against `h3` internals or silently weaken the capability gate.
3. **Do not migrate to s2n-quic solely for signaling.** Its transport is healthy, but its published H3 adapter inherits the same hyperium API gaps and adds a second migration.
4. **Keep Visitor carriage unresolved.** Before production selection, prove that its later chosen standard H3 mechanism can coexist with the signaling driver on the same connection. Reject any candidate that needs private raw stream use conflicting with the H3 implementation's stream dispatcher.
