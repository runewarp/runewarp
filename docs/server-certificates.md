# Server certificate ownership

Server ACME separates ordinary certificate serving from ACME driving. A replacement Server can serve an immutable, validated certificate/key snapshot while the previous process retains exclusive renewal ownership. Neither the snapshot nor the certificate controller carries Public hostname authorization, Client identities or ACME account material. Manual Server certificates, Client ACME and customer TLS passthrough retain their own paths.

## Ownership and persistence

Every cooperating owner on one worker must share the same private local `server.acme.state-dir`, including the same stable `owner.lock` inode. Core uses a nonblocking OS file lock. Ownership lasts until actual process exit, including after Managed drain, runtime cancellation or dropping a controller. Core deliberately retains its private descriptor for the process lifetime. There is no voluntary unlock, PID/age check, expiry, lease or file replacement that allows takeover. Do not unlink the lock, replace its directory, duplicate/pass its descriptor or fork an owner. Normal spawned executables do not inherit the descriptor. This is local cooperative ownership, not distributed locking or protection against nonparticipating software.

The state directory and its children must be private to the operator. Core creates directories with mode `0700` and material files with mode `0600`, rejects symlinks and non-private existing material, and requires Unix permission and directory-sync support. Use a filesystem whose local process-lock, atomic rename, file `sync_all` and directory `sync_all` semantics are supported. Network filesystems, physical power-loss behavior and storage-driver guarantees require their own validation.

`committed/generations/` retains at most two referenced complete cache generations. Each generation has an immutable owner cache blob and a separate `.pem` serving export containing only certificate/key material. Passive readers open only the manifest and serving export. Owner cache blobs bind the hostname, contact and CA directory and contain the account key and certificate state. A readable malformed account key blocks driving; Core does not silently replace it with a new account.

Publication writes and syncs both complete files, atomically renames them, syncs the generation directory, then writes and syncs the manifest candidate, atomically replaces `current.json`, and syncs its directory. The prior complete generation remains referenced. Candidate names are bounded; cleanup is synced before another publication. A crash before acknowledgment can recover either the old or new complete committed generation. Reopen rechecks material, repairs a missing/corrupt current generation from the prior complete generation where available, re-establishes durability and removes uncommitted candidates. A failed publication blocks export until reopen and recovery succeed. Never copy a live mutable `DirCache` file to warm another process.

## Process integration

The ordinary CLI Server path uses the controller too. It automatically attempts ownership, independently validates committed material using native system trust roots, and makes a real TLS connection through `server.hostname:443` to observe the consumed challenge route before polling ACME. This path uses Let's Encrypt production, a minimum remaining lifetime of 24 hours, a one-hour certificate safety margin, a five-minute recovery timeout and one-second retry intervals. A first boot stays unready until exclusive issuance and durable validation succeed. Public bind-port warnings remain advisory because ingress can map external TCP 443 to a different local port.

An embedding rollout caller uses `ServerRuntime::prepare_listeners_with_acme` and its `certificate_controller()` handle. `PreparedServer::bind_listeners_with_acme` exposes the same lower-level construction. `ServerAcmeOptions::new` selects explicit ownership requests, accepts the certificate trust/lifetime policy, HTTPS CA transport and `ChallengeRouteObserver`, and leaves ACME idle until `request_ownership()`. The normal QUIC and exact-Server-hostname TCP challenge resolvers are installed at initial bind. Activation never rebuilds a listener or restarts the replacement process.

`install_snapshot` revalidates an authenticated owner export for the receiver's exact hostname, signing-key correspondence, trusted chain, current validity and minimum remaining lifetime. Invalid replacement material leaves the last-good snapshot untouched. `CertificateSnapshot::to_pem` is private transport material and must never be logged. An owner can call `export_snapshot(required_remaining)` before drain to revalidate and confirm durable storage. This synchronous I/O operation belongs on a caller-owned blocking worker with a bounded pre-drain wait. It does not wait for a CA order to finish or promise that every renewal will complete.

The caller must include its entire warm, drain, takeover, finite recovery and clock allowance in `required_remaining`, and choose a compatible `CertificateValidation`, recovery timeout and safety margin. It must check replacement readiness and recovery prerequisites before irreversible drain. An export or readiness failure means aborting that planned drain while the old Server is usable. Core does not supply rollout phases, coverage policy, process supervision or ingress configuration.

After the old process exits, `request_ownership()` begins bounded takeover. The lock independently prevents ACME work before exit even if this request arrives early. Under ownership, Core loads and recovers its cache, installs an ephemeral owner-only TLS route proof and invokes the observer. The proof is never an ordinary serving certificate or valid ACME authorization. The observer must return the fingerprint it actually observed through the exact Server-hostname TCP `acme-tls/1` path and a bounded consumed route version. A desired configuration, promotion event, handling log or unverified marker is insufficient. The built-in `TcpChallengeRoute` checks the actual peer certificate and ALPN through the selected ingress. Its observation covers that network vantage; routed deployments needing an external routing authority must supply their external witness through the same production interface. The caller must keep that route stable and call `challenge_route_lost()` before revoking its evidence or changing it away from this owner.

Only then does Core create and poll ordinary rustls-acme state. Challenge TLS uses its active resolver only while this process owns the lock. Ordinary Tunnel TLS continues using the independently validated snapshot through slow/failed loading and acquisition. An active deployment event alone never replaces it. A cached candidate or newly stored certificate must independently pass validation and the durability barrier before ordinary serving changes. Snapshot material never answers an ACME challenge. Tunnel ALPN `h3`, pinned-identity mTLS and Public hostname passthrough remain separate.

`status()` reports certificate availability, ownership, driving, maintenance, fingerprint, expiry, consumed route version and sanitized failure reason. These facts are not rollout eligibility, application health or process-exit proof. Server readiness also requires a usable certificate when Server ACME is configured, alongside the existing Managed authorization gate. No snapshot means no ordinary Tunnel certificate and no readiness; the challenge path remains available for the sole owner's first issuance.

## Drain and failure recovery

Drain may interrupt acquisition or renewal. Dropping the polled rustls-acme state cancels its local futures; cache I/O workers remain covered by the process-held lock until they finish or the process exits. There is no remote cancellation, transferred order, in-flight observer or graceful quiesce guarantee. Abandoned and repeated CA orders are accepted. A drained process retains ownership until exit, and a drained Server never reopens admission.

The replacement keeps its validated snapshot while ownership, storage, routing or issuance recovers. Recovery has a finite monotonic timeout. Independent wall-clock checks also prevent new Tunnel handshakes and Visitor placement when the snapshot reaches its safety margin or is no longer time-valid. The runtime watchdog enters terminal maintenance and fast-stops ingress on either deadline; it does not resume the drained old process. Successful durable active validation ends that recovery attempt; later ACME failure starts another bounded recovery period. Core performs controller filesystem work on blocking workers so slow storage does not prevent its watchdog or live TLS handling from progressing.

Without a usable snapshot, including owner death before the first export, no traffic eligibility is inferred. The next process must acquire the lock, observe its consumed challenge route and successfully issue, validate and persist a certificate. Finite recovery can end in an explicit interruption and maintenance. Neither retained certificates nor these local tests establish seamless QUIC migration or general zero downtime.

## Sequential migration

Before overlapping with this implementation, stop every older binary that does not participate in `owner.lock`. Preserve the existing account/certificate cache and make the state directory private to its operator. Start one participating owner sequentially. Under the lock it can import and independently validate legacy `DirCache` account/certificate material into committed generations. Confirm a usable durable export before starting overlap. Never overlap a new owner with a nonparticipating old binary, and never copy the old binary's mutable cache files while it is running.

## Regression seams

- `CertificateOwner` is tested in real processes because only an OS lock and process death establish exclusion across runtimes.
- The public rustls-acme cache traits and filesystem adapter are tested with invalid material, read/write/rename/sync failures and process exit before and after publication boundaries because recovery must expose complete committed generations.
- `ServerRuntime` and `PreparedServer` are tested with real authenticated Tunnel handshakes, a consumed TCP ingress, a local TLS fake CA and a controlled certificate clock because utility-only tests cannot establish listener continuity, challenge ownership or admission shutdown. The fake CA validates CSR signatures and observes the real TLS challenge; it deliberately does not implement public-CA policy or JWS authentication. No public CA is needed.
